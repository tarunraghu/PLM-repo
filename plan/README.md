# POC plan (draft 3): 4 weeks

Status: draft for refinement. Nothing here has been run on Databricks yet. Product statements marked **verify** come from documentation or memory and must be checked in the workspace. See [architecture.md](architecture.md) for the diagram and [questions.md](questions.md) for open questions.

## Scope

For the John Deere PLM use case, a 4-week exploration of **Lakehouse RT**, **Lakebridge** and **Lakebase**, using synthetic data generated by `plmgen` and loaded through the medallion architecture (Bronze, Silver, Gold). Two use cases share one architecture: PLM part-design workflow (about 100 process steps per part) and Quality (PFMEA-style checks).

Team: Tarun and Hetvi. Work is tracked as Jira stories, with code in Bitbucket.

## Objectives

| # | Objective | Evidence we will produce |

| 3 | Understand what it takes to enable Lakehouse RT: latency, process and cost | enablement steps, who approves, time taken, limits, cost per hour or per query |

## Weekly plan

### Week 1 - data, medallion and access

Goal: data in Gold, and every gate that could block later weeks checked.

- **Check Lakehouse RT enablement on day 1**, and request it if needed. It is Beta and needs admin action, so waiting costs time.
- Confirm workspace access, a Unity Catalog catalog and schema, cost guard (auto-shutoff, budget alerts) and Lakebase branches (`production`, `devl`, `qual`).
- Finish the synthetic data design: add the process-step and quality domain to `plmgen` (parts, about 100 steps per part, workflow states, dependencies, milestones, quality checks). Same rules as today: truth stays clean, incremental equals one-shot, deletes are real.
- Generate the base extract and land it in a Unity Catalog volume. Build Bronze to Silver to Gold. Reconcile with the truth.
- Write the first findings: SAP PDM scope (objective 9) and Lakebridge's role (objective 10).
- Hetvi and Tarun: create the Jira epic and stories, and the Bitbucket repository and branch rules.

Done when: Gold tables exist and reconcile, RT status is known, Jira and Bitbucket are set up.

### Week 2 - dashboards and Lakehouse RT

Goal: objectives 2 and 3.

- Build the dashboard on the standard warehouse over Gold Delta tables. Pick 5 to 8 tiles that mean something for PLM: parts by lifecycle state, step status and age per part, quality check failures, change backlog.
- Build the same dashboard on Lakehouse RT (if enabled; if not, record the blocker and the wait time).
- Measure at several concurrency levels: first load, repeat load, filter change, and 1, 10 and 50 concurrent users. Record p50 and p95.
- Run `advance` and measure the time from a source change to the dashboard showing it, for both.
- Cost: capture cost per hour of each compute, idle cost, and scale-to-zero behaviour. Write the "what it takes to enable RT" note: steps, approvals, limits (read-only, no Genie, no external tables, Beta).
- Rehearse the Lakebase work locally while waiting on RT: PostgreSQL rehearsal with `plmgen lakebase` already works.

Done when: two dashboards exist, the latency and cost table is filled in, and the RT enablement note is written.

### Week 3 - Lakebase sync, both directions, and security

Goal: objectives 4, 5, 7 and 8.

- **Lakehouse to Lakebase:** create synced tables from Gold with each mode available (**verify**: snapshot, triggered, continuous; change data feed is needed for the last two). For each, record parameters, lag, compute cost, behaviour on updates and deletes, and failure recovery. Compare with the direct-apply path in `plmgen lakebase` as the fastest baseline.
- **Lakebase to lakehouse:** write through native Lakebase tables, then replicate back (**verify** the Lakehouse Sync requirements, such as replica identity full). Test updates and deletes.
- **Security:** create Postgres roles and grants in Lakebase, create the equivalent Unity Catalog row and column rules, and show a drift case (for example a plant-restricted user who sees different rows through each path).
- **Private endpoint:** find out how the Lakebase endpoint can be restricted to the client network and test it from inside and outside.
- Token life (one hour), idle timeout and maximum connection life must be handled in long runs.

Done when: a sync mode comparison table, a working return path, a security drift example, and a private-access design with test results.

### Week 4 - low-latency updates, end to end, write-up

Goal: objective 6, then conclusions.

- **Micro-batch simulation with Lakebase as the ODS.** Run bursts of changes (`--activity 3`) across simulated SAP PDM, Windchill, part release and program management. Show one change in one system appearing in the others, measure lag at each stage (source, ingest, transform, sync, app), and test windows of 1, 5 and 15 minutes.
- **Updates and deletes** to the product lifecycle reflect and match the truth (`lakebase verify`).
- End to end run for both use cases, with the app-side queries and a write back.
- Decide the recommended freshness target per class (transactional approvals versus orchestration) from the measured numbers.
- Write the findings and the recommendation: architecture decisions, trade-offs, limits, cost, risks. Prepare the internal architecture review.

Done when: the end-to-end run is repeatable, the recommendation document is drafted, and the review is scheduled.

## Cross-cutting

- **Cost.** Every compute has auto-shutoff and a budget alert before any long run. A prior weekend incident cost about $10K, so check consumption daily.
- **Latency stages.** Always report lag per stage: source to landing, landing to Bronze, Bronze to Gold, Gold to Lakebase, Lakebase to app. One end-to-end number hides where time goes.
- **Findings log.** One running list of each limit found, with evidence and the workaround.
- **Jira and Bitbucket.** One epic per objective group, stories per week, acceptance criteria taken from the "Evidence" column above.

## Risks

- RT enablement delay: it is Beta and needs admin action. Weeks 3 and 4 must not depend on it.
- Scope creep: even a small change touches many systems. Keep to one pattern and two thin use cases.
- Private networking may need the client's network team, which can take longer than a week.
- The diagram says "single security model across ODS and lakehouse". Expect to find that this does not hold, and report it early.
- Unverified product details (sync modes, Lakebridge, RT limits) may change. Check before building on them.
